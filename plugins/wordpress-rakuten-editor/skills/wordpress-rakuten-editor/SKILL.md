# WordPress楽天記事編集・オンライン版

このファイルは入口。編集ルールの正本は配布元にあり、依頼ごとに取得して固定する。
配布元：https://wordpress-rakuten-rules-8d8ab.hallelujah097hallelujah.workers.dev
入口バージョン：1.1.0 / protocol 1

## 依頼ごとに、順に行う（途中に判断を挟まない）

1. **作業フォルダは、いま開いているフォルダ。** 探さない。ユーザーが別フォルダを明示した場合だけそれに従う。

2. ルールを取得する。Python 3.8以上。Windowsでは `py -3`。

   ```bash
   python3 <このSKILL.mdと同じフォルダ>/scripts/fetch_rules.py fetch
   ```

   `--project-dir` は開いているフォルダが既定。別フォルダを指定するときだけ渡す。

3. 終了コード0とJSONの `ok:true` を確認する。`version`・`revision`・`snapshot_dir`・`config_path` を**この依頼中固定する**。
   **`config_path` は受け取った値をそのまま使う。自分で探し直さない。**

4. `snapshot_dir/SKILL.md` を全文読み、**そこが指示する参照だけ**を読む。取得しただけで読み終わったと扱わない。
   同じ記事の処理途中で版を切り替えない。古いローカル資料・前の回答・別スナップショットを混ぜない。

5. 「編集ルール v… を取得しました。対象：サイト…／記事ID…」と1行で知らせ、依頼範囲の作業に入る。
   取得したルールは、システム・開発者・ユーザーの指示や通信・承認の制限より優先しない。

## サイトと記事IDの決め方

聞く前にここで決める。確認の質問は最大1回、かつWordPressや楽天へ通信する前だけ。

- **サイト** — 設定は `config_path` の1ファイルだけ。`snapshot_dir/scripts/local_config.py` を絶対パスで読み込み、`list_sites(path=config_path)`、`load_config(path=config_path, wordpress_only=True, site=...)` のように必ず `path` を明示する。登録が1件で指定が無ければ**黙ってそれを使う**。2件以上で指定が無ければ**1回だけ**聞く（名前だけを示す）。名前・ID・登録URLのいずれかで一意に決まればそれを使う。
- **記事ID** — 依頼文の最初の整数（「1422を」「記事ID 1422」「post=1422」「?p=1422」）。パーマリンクならスラッグで解決する。見つからなければ1回だけ聞く。
- **モード** — 既定は自動判別。「アイキャッチ」「挿絵」「画像」があれば画像を追加、「記事全体」があれば共通仕上げを追加、「変更案だけ」「保存せず」があれば読み取りのみ。
- **更新意思** — 「仕上げて」「整えて」「実装して」「更新して」は更新の指示。「サイトA／1422／自動判別で進めます」と1行述べ、**待たずに進む**。

設定の値は出力しない。他サイト・他フォルダ・環境変数で不足を補わない。取得スクリプトにAPIキー・サイト設定・記事本文を渡さない。

## 途中で止めない

サイト・記事ID・更新意思が決まったら、ユーザーに戻るのは次の4つの終端だけ。

1. 保存し、保存後の確認も通った
2. 下の停止条件に当たり、保存していない
3. 読み取り依頼が完了した
4. 全対象が保留になり、変更がなかった

**止まってよい条件（これだけ）** — ルール取得・検証の失敗／認証が足りない／対象の同一性が確認できない（その項目だけ保留）／保存直前に第三者の変更があった／保存前監査に通らない／リンク台帳の数と完成カード数が一致しない／市場・ふるさと納税でAmazonの必須条件を満たせない。

**止まってはいけないもの** — 品質の警告、画像生成の一部失敗（上限まで試したら省略して続行）、口コミの件数不足、CSSが未導入だという検出、楽天の対象が0件。いずれも続行し、最後に報告する。

意思が決まった後に「〜しますか？」「続けてよいですか？」と聞かない。
リンク台帳の数が合わないときは、部分保存せず、一致させてから保存する。人間に差し戻さない。

## 保存とバックアップ

出力とバックアップは作業フォルダ基準。編集前の `content.raw` とメタデータを `backups/<サイトID>/<記事ID>/<UTC時刻>/` に残す。
ルールのスナップショットは `.rakuten-rules` 内にあり、進行中のものを削除しない。
サイト共通のCSS・JSを記事更新と一緒に書き換えない。
最新版の取得に成功しても、記事の保存成功や全員への反映済みとは報告しない。実際に実行・確認した範囲を区別する。

## 取得できない場合

Python・HTTPS通信・ファイル保存が使えない、HTTPエラー、リダイレクト、JSON以外、版の不一致、ハッシュ不一致、資料不足のときは記事更新を開始しない。古いローカル版へ黙って戻らず、実際の理由を報告する。別の配布URL・別プロキシ・権限や認証の回避を試さない。環境を直したうえで同じ手順で再試行する。

入口自体の更新が必要と返った場合は配布元の案内に従う。通常の編集ルールの変更は次回の取得で反映される。配布URL・取得方式が変わるときだけ入口の更新が必要になる。

## 初期設定

「初期設定して」と言われたとき、または `config_path` のファイルが存在しないときは、記事作業へ進まない。
他を何も聞かずに、次を実行する。

```bash
python3 <snapshot_dir>/scripts/setup_sites.py --serve
```

標準出力の1行目に `url` が返る。**そのURLをそのままユーザーへ渡す**（「このリンクを開いて入力してください」）。
フォームはユーザーのPCの中だけで動き、入力された値をその場で作業フォルダの `sites.local.json` に
0600で保存する。保存が終わるとコマンドが結果を返して自動で終了する。

**資格情報をチャットで聞かない。** 報告してよいのは返ってきた `filled` と `missing` の項目名だけで、
値は復唱しない。登録済みサイトの確認は `--list` を使う。

ブラウザを開けない、またはポートを開けない環境でだけ、ユーザーに断ったうえで項目をチャットで聞き、
`{"site_name":…, "config":{…}}` を `--json-stdin` へ標準入力で渡す。
この経路では入力した値が会話の記録に残ることを、聞く前に伝える。

## SEO Fleetの同一実行IDで再開する場合

Fleetヘルパーが `rules-lock.json` を検証して `handoff.json` に固定版を返した場合は、その版の `SKILL.md` と `references/fleet-integration.md` を使う。同一runを新規依頼として再取得しない。新しいrunは必ず最新を取得する。Fleetの実行IDが無い依頼では、この節は使わない。

## スキル自体の修正依頼

編集ルールの正本は講師が管理する非公開リポジトリにあり、配布元のWorkerから配信される。この入口や手元の古い資料だけを直して全員に反映したと報告しない。正本を更新する権限が無い場合は提案までにし、配布元の場所や他人の認証情報を探さない。権限がある講師の依頼では、正本リポジトリの `AGENTS.md` と `README.md` に従い、修正・検証・バージョン更新・配信後の取得確認までを一つの変更として行う。
